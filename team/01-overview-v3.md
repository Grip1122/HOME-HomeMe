## 修订 1（10/31）· 场景改为高斯泼溅，取消灰盒

**本版起，方案以建筑高斯泼溅素材 `scene.ply` 为唯一场景来源，不再有"程序生成灰盒房间"这一阶段。** 授权已确认为开源素材，可直接使用。

由此产生的五处变动，后文对应小节已同步改写：

| 变动 | 原方案 | 现方案 |
| --- | --- | --- |
| 场景来源 | 按 layout 矩形程序生成地板与墙体（灰盒） | 直接渲染 `scene.ply` 重建出的真实建筑 |
| 家具表现 | 立方体灰盒 → 阶段 5 换成 GLB 模型 | **真实家具已在点云里，不再放 GLB**；layout 只提供**隐形碰撞体与台面高度** |
| 坐标标定 | 手写矩形，坐标自定 | 必须先把 layout 坐标对齐到点云实测位置（含缩放系数） |
| 阶段 5「美术替换」 | 灰盒换低多边形资产 | 取消。改为"泼溅质量调优"（抽稀、分块加载、曝光与色调） |
| 降级预案 | 掉帧时回退灰盒 | 掉帧时**抽稀高斯点**或降为静态截图贴图；灰盒不再是选项 |

**不变的部分**：五个动作语义、状态机、`/plan` 契约、纠错强规则、记忆模型、测试与守门设施、以及"逻辑与视觉解耦"这条原则。逻辑层仍然只读 layout JSON，**不读点云**——这是点云方案能安全落地的前提。

**新增的硬约束**：点云不提供碰撞、不提供语义。所以 layout 里的 `blocks` / `surface` / `size` 现在承担全部逻辑真值，它的准确性从"够用"上升为"必须"。

## 给 Agent 的统一说明（所有人通用，先读这个）

**你（Agent）的角色**：按契约交付代码的外包工程师，只负责下发给你的那一个模块。

**必须遵守的五条（违反即被打回）**

1. **`contracts/` 只读。** 不得修改其中任何文件。认为契约有问题时，**停下来**，只输出「契约问题说明」（哪一行、为什么、建议怎么改），**不要**写绕过它的代码。
2. **只改自己目录。** 越界改别人模块 = 打回。需要别人配合就在输出里写明"需要 xxx 提供 xxx"，不要代劳。
3. **必须带能失败的测试。** 每个模块至少三条（正常 / 边界 / 异常）；异步代码测「中途取消」和「并发调用两次」；状态机测「非法转移」。测试名写成句子。
4. **不得为了跑通而放宽 Schema、删除断言、改测试预期。**
5. **不得新增依赖**，除非在输出里单独说明理由并等人确认。

**每次交付的输出格式**

- **A** 完整代码
- **B** 测试文件（每条验收一个 test，名字写成句子）
- **C** 「我做了哪些假设」——列出你自己补的所有前提
- **D** 「故意改错」演示：指出你改坏了哪一行、哪个测试因此变红、终端输出是什么

**人类侧流程（你的主人会做）**：`git switch -c feat/<步骤号>-<短名>` → 提交（带 `Authored-by:` 行）→ `git push -u origin 分支` → `gh pr create --fill --base main` → 等 CI 四个 job 全绿 → 把关人审核合并。

| 执行底线 |

**表 1 本版三条改进与预期收益**

| 序 | 改进 | 要解决的问题与做法 |
| --- | --- | --- |
| 1 | 逻辑与视觉解耦 | 网格外扩 0.25 米只保证身体不撞家具，抓取时手仍会穿进家具或位置偏移。改为：判定只看水平距离小于 1 米；相机固定 45 度正交俯视且禁止旋转；抓取用 Punch 前半段快速过渡、物体缩到 0.4 倍；物体一律用保持世界变换的挂载；抓取期不加任何发光特效。 |

# 一、项目总览与系统架构

## （一）一句话定义

用户用自然语言（文字或语音）让虚拟管家"小方"在三维家庭中找东西、拿东西、放东西；小方会记住物品位置，记错了能被纠正，换了房间布局照样能干活。

## （二）团队角色与接口边界

角色划分的原则是"按模块切、不按层切"：每个人对自己模块从数据到界面负责到底。V3 在此基础上补一列**接口边界**——它比"主责"更重要，因为它决定了谁不能改什么，而 Code Review 的第一关就是查越界。

**表 2 四名成员的角色、主责目录与接口边界**

| 代号 | 角色 | 主责目录 | 只通过契约对外提供 | 不得触碰 |
| --- | --- | --- | --- | --- |
| 设计 A | 前端与 3D 交互工程 | web/src/core/<br>web/src/robot/<br>web/src/nav/ | 事件总线事件（contracts/events.md）、五个动作的 Promise 语义、状态机状态名 | scene/、ui/、server/、contracts/ |
| 设计 B | 场景与美术建模 | web/src/scene/<br>web/public/ | layout JSON 实例、点云接入与坐标标定结果、物体与家具的隐形包围盒约定 | robot/、nav/、server/、contracts/ |
| 设计 C | 产品设计与 UI | web/src/ui/<br>web/src/demo/<br>docs/ | HUD 组件、对话与气泡文案、导演面板、验收用例与路演稿 | robot/、nav/、server/、contracts/ |
| AI-D | 后端与算法 | server/ scripts/ tests/ .github/ | POST /plan 响应、/memory 读写、纠错规则、布局校验脚本 | web/、contracts/ |
| 把关人 | 审核与集成（你） | contracts/（唯一有权最终合并） | 合并决定、里程碑 tag、契约变更裁决 | 不直接写业务代码，避免既当运动员又当裁判 |

四条边界的处置办法：

1. 契约只读：四个人都不能在自己分支里顺手改 contracts/。要改就单开 contract/ 分支，只含 contracts/，由把关人合并。机器拦截方式见第十六章。
2. 跨模块需求：改别人模块的代码是最常见的越界。正确做法是提 issue 或直接在群里说，由 owner 自己改；实在来不及，owner 明确授权后由授权人改，并在 PR 里 @ owner。
3. 共享文件：docs/test-cases.md 由设计 C 主笔，其他人只能提 PR 补充；scripts/ 归 AI-D，别人要加脚本先说明用途。
4. 同时只开一个分支：分支活过 4 小时视为风险，要么拆小合并，要么废弃。这条是为了让把关人的审核队列永远是短的。

## （三）系统架构

系统分为四层，自上而下单向依赖。这条单向依赖是本项目能被四个人并行开发的结构性原因：下层不知道上层存在，上层只通过契约调用下层。

**表 3 四层架构**

| 层 | 组成 | 职责 | 所在端 |
| --- | --- | --- | --- |
| 交互层 | 输入框、语音按钮、HUD、导演面板 | 接收指令、展示状态 | 浏览器 |

# 二、核心建模

本节是整个项目的技术地基。六个模型在一次讨论中定死，后续所有代码都只是它们的实现；模型一旦反复变动，四人并行就会失效。

## （一）场景数据模型

整个世界由一份 layout JSON 描述。前端加载它生成场景，后端读取它做规则解析与校验，两端共用同一份真值。V3 在三处补强：门洞、分区默认落点、别名表——它们分别对应"换房间能不能走过去""说放书房放到哪""杯子/水杯是不是同一件"这三个真实问题。

```
contracts/layout.example.json（节选，与仓库一致）
{
 "layout_id": "A", "version": 1,
 "grid": { "cols": 24, "rows": 18, "cell": 0.5, "origin": [-6.0, 0.0, -4.5] },
 "rooms": [
 { "id": "living", "name": "客厅", "aliases": [], "rect": [0, 0, 12, 18],
 "scan_point": [-1.5, 0.0, 0.0], "drop_to": "table_coffee" },
 { "id": "bedroom", "name": "卧室", "aliases": ["房间"], "rect": [12, 0, 12, 9],
 "scan_point": [3.0, 0.0, -1.5], "drop_to": "nightstand" },
 { "id": "study", "name": "书房", "aliases": [], "rect": [12, 9, 12, 9],
 "scan_point": [3.0, 0.0, 2.0], "drop_to": "desk" }
 ],
 "doors": [
 { "id": "door_living_bedroom", "between": ["living", "bedroom"],
 "pos": [0.0, 0.0, -2.25], "width": 1.5, "axis": "z" },
 { "id": "door_living_study", "between": ["living", "study"],
 "pos": [0.0, 0.0, 2.25], "width": 1.5, "axis": "z" }
 ],
 "furniture": [
 { "id": "table_coffee", "name": "茶几", "aliases": [], "room": "living",
 "pos": [-4.0, 0.0, -0.3], "size": [1.2, 0.45, 0.6],
 "blocks": true, "surface": true, "model": "kenney/tableCoffee.glb" }
 ],
 "objects": [
 { "id": "cup_red", "name": "红色水杯",
 "aliases": ["水杯", "杯子", "红杯子", "红色杯子"],
 "room": "living", "pos": [-3.0, 0.75, 2.85], "on": "table_dining" }
 ],
 "stains": [ { "id": "stain_1", "room": "bedroom", "pos": [2.4, 0.01, -1.0] } ]
}
```

建模六条要点：

1. 坐标单位统一为米，y 轴向上；网格只管 x-z 平面。家具的 pos 是包围盒底面前左角，size 是宽高深。
2. 家具分两类属性：blocks 决定是否占据寻路格子，surface 决定能否放东西。放置动作只允许落在 surface=true 的家具上。
3. 门洞决定跨房间可达：doors[] 声明哪两个分区间有洞、洞心位置与宽度。跨分区的相邻格只有在门洞范围内才连通，否则视为墙。宽度下限 1.0 米（外扩 0.25 米后仍留 0.5 米净宽），由校验脚本强制。
4. 分区默认落点：drop_to 让"把书放到书房"这种只说分区的指令有确定答案，不用让模型猜，也不用临场加规则。
5. 别名表：物体与地点都带 aliases，规则解析与提示词共用，解决"杯子、水杯、红杯子"指同一物体的问题；别名在全局必须唯一，否则"放到 X"会有歧义。
6. 每个分区有扫描点：全屋扫描就是依次走到各分区扫描点并执行一次 observe；扫描点必须落在本分区、不压在阻挡格上、且与其他扫描点互通。
以上六条不是约定，而是脚本：`scripts/check_layout.py` 对示例布局做八类检查（分区重叠、别名重名、家具越界、阻挡家具重叠、门洞过窄、扫描点不可达、物体悬空、物体够不着），任何一条不满足直接失败。这套检查本身也有"能失败"的证明，见 0.4 节。

## （二）规划契约

这是前后端之间唯一的接口。契约冻结后，AI-D 可以独立开发后端，设计 A 可以独立开发执行器，两人不需要等待对方。V3 新增三个字段，都是为纠错服务的。

```
POST /plan 请求与响应（V3）
请求 {
 "query": "不对，应该放书房",
 "layout_id": "A",
 "memory": [ { "object_id": "cup_red", "room": "living",
 "pos": [-3.0, 0.75, 2.85], "confidence": 0.85 } ],
 "memory_enabled": true,
 "last_object": "cup_red", // V3 新增：上一任务操作的物体
 "robot": { "pos": [0, 0, 0], "holding": null }
}
响应 {
 "say": "抱歉，我记错了。这就把红色水杯放到书桌。",
 "steps": [
 { "action": "go", "target": "cup_red" },
 { "action": "grab", "target": "cup_red" },
 { "action": "go", "target": "desk" },
 { "action": "drop", "target": "cup_red", "to": "desk" }
 ],
 "source": "corrective", // V3 新增枚举值：永不来自大模型
 "corrected": true, // V3 新增
 "corrected_object": "cup_red", // V3 新增
 "corrected_to": "desk", // V3 新增
 "latency_ms": 2
}
```

三个新字段的分工：`last_object` 解决"不对，放书房"没提物体的问题（纠正句最常省略宾语）；`corrected` 系列让 HUD 与日志能区分"照着做"与"改过来做"；`source=corrective` 让现场一眼看出这句话没走模型。

动作集仍是五个，语义定义如下。

**表 5 五个动作的语义与后置条件**

| 动作 | 参数 | 前端行为 | 后置条件 |
| --- | --- | --- | --- |
| find | target | 有可信记忆则走到记忆位置并观察；没有或观察落空则按分区扫描直到发现 | 机器人站在目标旁 |
| go | target（家具 / 物体 / 分区） | 寻路走到目标的可达邻格；目标是分区时走到扫描点 | 机器人到达 |
| grab | target | 水平距离小于 1 米即判定可抓；播放 Punch 前半段快速过渡，物体挂到携带锚点并缩到 0.4 倍 | holding = target |
| drop | target、to | 先 go 到 to，再播放放置动画，物体挂回家具并落到台面高度，缩放恢复 | holding = null |
| observe | room（可选） | 原地环顾，返回可见物体列表并写入记忆 | 记忆更新 |

`find` 把"去哪找"的决策留在前端执行器而不是大模型，这是 V2 最关键的设计：大模型只负责理解意图，空间推理交给确定性代码。V3 把这条原则延伸到纠错——"改去哪放"同样交给确定性规则，模型连建议权都不给。

## （三）机器人状态机

状态机是防止"连点抽搐""物体粘手"的唯一手段。三条规则必须写成代码而非约定：任何外部请求只能入队、不能直接改状态；状态机每帧只处理队首任务；切换状态统一做动画淡入淡出，时长 0.25 秒。

**表 6 机器人状态与转移**

| 状态 | 进入条件 | 动画与表现 | 可转移到 |
| --- | --- | --- | --- |
| idle | 初始或任务完成 | Idle | thinking |
| thinking | 收到指令、等待 /plan | Idle 加头顶思考气泡 | walking、confused |
| walking | 执行 go 或 find 的移动段 | Walking | scanning、picking、placing、idle |
| scanning | 执行 observe | Idle 加原地转身 | walking、confused、idle |
| picking | 执行 grab | Punch 前半段，总时长不超过 0.5 秒；物体缩到 0.4 倍；无发光 | walking、idle |
| placing | 执行 drop | Punch 反向或 Wave，同样不超过 0.5 秒；缩放恢复为 1 | idle |
| confused | 记忆落空、规划失败、澄清 | Sad 表情加 No 动作 | scanning、idle |
| celebrating | 任务完成 | ThumbsUp | idle |

状态机用转移表实现（一个对象字面量描述每个状态可去往哪些状态），比条件分支更易审查与测试。每条非法转移必须抛错并记录，测试里要有"非法转移"用例——AI 生成的状态机最常见的两种病是"某个状态没有出边导致死锁"和"出边条件互斥导致永远进不去"，这两条只有测试能抓出来。

## （四）寻路算法

采用网格 A* 而非导航网格，理由有三：家庭场景是规则矩形，网格足够；网格可直接由 layout 的 blocks 家具生成，零烘焙步骤；出了问题肉眼可调。若后续换成不规则户型，再迁移到导航网格方案。

1. 建网格。24×18 格、每格 0.5 米。遍历 blocks 为真的家具，把其包围盒外扩 0.25 米（机器人半径）覆盖的格子标为不可通行。注意这只保证身体不撞家具，不保证抓取时手不穿模——后者由第 2.7 节处理。跨分区的相邻格只有落在 doors[] 范围内才连通。
2. 求路径。用 PathFinding.js 的 AStarFinder，允许对角移动但禁止穿角。
3. 平滑。用库自带工具去掉冗余拐点，再转成世界坐标。
4. 定终点。目标是家具或物体时，取其所在格周围最近的可通行格，避免终点落在家具内部而无路可走。
5. 移动。沿路径用补间逐段插值，速度 1.2 米每秒，朝向用四元数球面插值平滑转身。

## （五）空间记忆模型

```
SQLite 表结构（V3：新增 status 列）
CREATE TABLE spatial_memory (
 layout_id TEXT NOT NULL,
 object_id TEXT NOT NULL,
 room TEXT NOT NULL,
 pos_x REAL, pos_y REAL, pos_z REAL,
 confidence REAL NOT NULL DEFAULT 0.8,

);
CREATE TABLE task_log (

);
```

置信度更新规则全部是确定性公式，可写成单元测试，不依赖任何模型判断。六条规则各配一条测试，已在本版仓库的 `server/app/memory.py` 与 `tests/test_planner_offline.py` 中实现并通过（其中三条被变异验证证明"改坏就会红"）。

**表 7 置信度更新规则**

| 事件 | 更新公式 | 说明 |
| --- | --- | --- |
| 观察首次看到 | c = 0.80 | 新建记录，status=fresh |
| 到达记忆位置且看到 | c = min(1.0, c + 0.05) | 强化 |
| 到达记忆位置但没看到 | c = c − 0.40，status=stale | 弱化并触发全屋复扫 |
| 扫描在新位置看到 | 覆盖位置，c = 0.80，status=fresh | 重建 |
| 用户纠正 | 旧位置 c − 0.30；新位置 c = 0.90 | 人类反馈权重最高，source=correct |
| 读取时 | c 低于 0.30 视为无记忆 | 阈值 |

"训练前后对比"的定义在此明确：同一 layout、同一指令、同一初始物体位置，仅切换 `memory_enabled`。关闭时 find 必然走全屋扫描，开启时直达。两次执行的步骤数与耗时都来自真实日志，HUD 直接读表展示，不做任何美化。

## （六）规划与降级算法

V3 把流水线从"缓存优先"改成"纠错判断前置"。原因很直接：纠错句如果先进缓存或进模型，就会出现"模型把'不对'理解成一句新的找物指令"这种荒谬结果。纠错是最高优先级、且完全确定的一档。

```
规划流水线（V3，五档）
0 纠错判断（前置，永不跳过）
 is_correction(query) 为真 -> 走第 2.8 节强规则，source=corrective，直接返回
 命中后不进缓存、不进模型；本地耗时 < 5 ms
1 缓存命中
 key = normalize(query)，【不含】记忆快照与 layout 摘要
 五句核心台词在彩排后固化进 server/app/cache.json
2 在线规划（可选，可关闭）
 GLM，system 含动作定义 + 别名表 + 家具表 + 3 示例；只输出 JSON；超时 2.5 秒
3 结构校验 + 语义校验
 JSON Schema 管字段与枚举；语义管 target/to 存在、drop 前必须 grab、to 必须 surface
4 规则解析（source=rule）
 正则匹配 "找|拿|把 X 放到 Y" 等句式，X/Y 用别名表模糊匹配
5 仍失败 -> say="我没听懂，可以换个说法吗？"，steps=[]，播放 confused
```

缓存的键为什么要剔除记忆快照：V2 的键是 `hash(query + layout_id + 记忆摘要)`，而记忆会被观察不断更新，键随之漂移，固化好的缓存就命不中了——这是"彩排时好好的，现场就不灵"的典型来源。剔除之后，记忆只影响 find 的走法（走到哪个位置），不影响 steps 的结构，因此同一句台词的结果可以稳定复用。

出口再校验一次：任何来源（缓存、模型、规则、脚本）的 steps，在返回前都要过一遍语义校验；不通过就降级为澄清。这条是"最后一道闸"，防止有人往 cache.json 里塞了一条非法步骤而没人发现。测试里有一条专门的"投毒缓存"用例守着它。

## （七）视觉表现规则：逻辑与视觉解耦

这是本版新增的第一条硬规则。它要解决的不是"看起来不够真"，而是"评委一眼看出手穿进了茶几"。核心判断：**寻路网格外扩 0.25 米只保证机器人的身体不撞家具，它从来不保证手伸出去不穿模。**用碰撞检测去解决抓取的视觉问题，成本极高且几乎不可能在 26 小时内调好；正确做法是让视觉"不被看见"。

**表 8 逻辑层与视觉层的职责切分**

| 层 | 负责 | 明确不负责 |
| --- | --- | --- |
| 逻辑层<br>nav/ robot/actions.js | 能不能抓、抓谁、状态转移、记忆更新 | 手长什么样、有没有碰到家具 |
| 视觉层<br>robot/animation.js | 看起来像在抓、过渡是否顺滑 | 判定是否成功；不得向逻辑层回传任何信息 |

**抓取判定。**水平距离小于 1.0 米即可抓。用水平距离而不用三维距离：物体在桌面上、机器人在地面，高度差是正常的，算进去会永远判不够。不满足时先 `go(target)` 走到最近可达格再判一次，仍不满足则返回 `{ok:false, reason:"too_far"}`。示例布局里八件物体到最近可站格的距离是 0.60 至 0.93 米，都满足阈值；这个区间由校验脚本持续守着，布局改坏（例如把笔记本塞进床和墙的夹缝，距离变成 2.0 米）会直接报错。

**固定相机。**正交投影、固定 45 度俯仰，只允许平移与缩放，禁止旋转与倾角。

**表 9 相机参数（固定，不开放给现场操作）**

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 投影 | OrthographicCamera | 无透视形变，手与家具的前后关系恒定 |
| 俯仰 | 45 度，固定 | 看不到桌下、柜背、物体底面 |
| 偏航 | 固定，enableRotate=false，且 minPolarAngle = maxPolarAngle | 评委无法转到穿帮角度 |
| 允许操作 | 平移、缩放 0.7–1.5 倍 | 够用，且不会把镜头拉到贴地 |

**抓取动画。**只用 Punch 的前半段，总时长不超过 0.5 秒（含 0.25 秒淡入淡出）；抓取瞬间把物体缩到 **0.4 倍**，放置后恢复为 1。

**不加发光特效。**发光会在物体与手之间形成一条高亮接触线，等于主动给观众标出穿模的位置。抓取阶段最好的表现是"快、小、没有额外提示"。目标物高亮仍保留，但只用于"找到了"那一刻，与抓取动画在时间上错开，不叠加。

**挂载必须保持世界变换。**这是最容易出错、也最容易测的一处：

```
挂载写法（three.js）
// 正确：attach() 会重算局部变换，世界位置保持不变
carryAnchor.attach(objectMesh)

// 错误：add() 不改局部变换，物体会瞬移到锚点局部坐标
carryAnchor.add(objectMesh)

// 放置同理，且把"贴台面"单独写成一步，便于测试
furnitureGroup.attach(objectMesh)
objectMesh.position.y = furnitureTopY
objectMesh.scale.setScalar(1)
```

**必须有的测试**：挂载前后记录物体的世界坐标，断言差值小于 1e-6。这条测试能抓住所有"用了 add 就瞬移"的 AI 生成代码，成本只有几行。

**这套方案的边界要说清楚**：它不消除穿模，只让固定视角下看不出来。一旦允许自由旋转或切到第一人称，穿帮立刻暴露；那时必须回到真正的 IK 或接触约束。演示方案选择"锁死视角"，是因为在 26 小时的窗口里，可验证的确定感比自由度更值钱。

## （八）纠错强规则：不依赖大模型的固定流程

这是本版新增的第二条硬规则。V2 的 3.4 把"无法识别的纠正"交给大模型，问题有两个：延迟不可控（现场 2 至 3 秒的沉默很难看），以及幻觉（模型可能把"不对"理解成一次新的找物，甚至编出一个不存在的家具）。V3 的处置是：**纠错路径彻底不走模型，用正则加重名词典，输出固定步骤模板。**

**表 10 纠错处理流程（五步，全部本地）**

| 步 | 动作 | 规则 |
| --- | --- | --- |
| 1 | 判定是否纠错 | 硬否定词（不对 / 不是 / 错了 / 放错 / 别放 / 不要放 / 不应该）出现即判为纠错；软改写词（应该 / 挪到 / 移到 / 搬到 / 改放）只在"无祈使包装且不超过 10 字"时才算，避免把"帮我把书搬到卧室"当成纠错 |
| 2 | 抽取新地点 | 用地点词典（分区名 + 别名 + 家具名 + 别名）匹配，取最后一个未被否定的地点；"不要放茶几，应该放书房"取书房，"应该放书房，不要放茶几"也取书房 |
| 3 | 抽取物体 | 先用地点的字符区间做遮罩，再匹配物体词典——"书房"里的"书"不能被当成蓝色书；句中没有物体时用请求里的 last_object |
| 4 | 解析落点 | 地点是分区则取该分区的 drop_to；是家具则必须是 surface=true，否则回一句"沙发上放不了东西" |
| 5 | 下发固定步骤 | 手里正拿着该物体：go(新地点) + drop；物体已放下：go(物体) + grab + go(新地点) + drop。同时调用记忆纠正接口（旧位置 −0.30，新位置 0.90） |

**为什么第二种模板要多两步。**需求里写的是"强制下发 go(新地点) + drop 的固定步骤"。这在机器人已经拿着物体时完全正确，但 V2 的演示流程里，用户纠正发生在"已经放到茶几上"之后——此时机器人手里是空的，直接 `go + drop` 会被语义校验拦住（drop 前必须 grab），现场表现为"说了抱歉但什么都没发生"。所以本版把它写成**按 holding 分支的两套固定模板**，主路径仍是 go + drop，另一条只是必要补全。

**失败时就问，不猜。**以下情况一律返回澄清而不是硬猜：只说了"不对"没说地点；说的是沙发这类不可放置的家具；没提物体且没有 `last_object`。澄清话术固定三句，写死在代码里，不调模型。

**与缓存的配合。**纠错路径**不进缓存**（每次都要按当时的 holding 与 last_object 重算，缓存反而会错），但对应的五句核心台词固化在 `server/app/cache.json`，键为标准化的 query（去标点、去"小方/请/麻烦"等唤醒词、小写）。固化台词的口径是"结构固定、措辞固定、耗时固定"，目的是让彩排与现场完全一致。

**实测数据**（本版仓库，`tests/test_rules_correction.py`）：覆盖 30 余条用例，包含否定在前、否定在后、地点含物体字、省略宾语、不可放置家具、普通搬运指令不得误判等边界；单次判定平均耗时低于 0.1 毫秒。其中"普通搬运指令不得误判"这条是实测踩出来的：第一版把"搬到/移到"直接当否定词，"帮我把书搬到卧室"会回一句"抱歉，我记错了"，非常突兀，已修正并加了回归用例。

# 五、阶段 1：骨架

## （一）步骤 1.1 场景加载器（高斯泼溅 + 隐形碰撞层）

> **已按修订 1 改写**：不再生成灰盒房间。

**目标与内容。**加载高斯泼溅建筑，叠加一层不可见的碰撞与语义层，并建立物体注册表。

1. **点云层**：加载 `scene.ply` 的转换产物（`.splat` / `.ksplat`，转换与渲染器选型见 `assets/gaussian-splat/`）。换算 `sceneScale`、`sceneOffset`、`upAxis`，使点云与 layout 坐标系对齐——这三个常量只在 `core/config.js` 定义一处。
2. **碰撞层**：按 layout 的 `blocks` 家具生成**不可见**包围盒（`material.visible = false`，但保留在场景图中），供寻路与射线检测使用。**真实家具已在点云里，不要再放 GLB 模型**，否则会出现"两套家具"错位。
3. **台面层**：`surface=true` 的家具生成不可见台面平面，物体落点取该平面高度。
4. **语义层**：门洞按 `doors[]` 生成不可见通行区，跨分区连通性由它决定，而不是由点云有没有缝决定。
5. **物体**：8 件任务物体仍用彩色小几何体（红色圆柱、黄色方块），保证俯视角下一眼可辨——它们需要明显区别于点云。
6. **注册表**：按 id 取对象 / 按分区列出物体 / 取世界坐标。
7. **相机**：正交投影、固定 45 度俯仰、禁用旋转与倾角，只允许平移与缩放 0.7–1.5 倍；参数只在 `core/config.js` 定义一处。

**点云与固定相机可能冲突。**高斯泼溅按屏幕空间深度排序，**正交相机下可能出现前后遮挡错误**。这一步必须实测；若不成立，本节第 7 条与第 2.7 节的"锁死视角规避穿模"方案都要重设计。

**完成标准与交付物。**切换布局能看到对应房间的点云画面，不可见碰撞层与点云中真实家具对齐（用网格辅助线肉眼比对）；控制台调注册表能取到指定物体。交付物为点云加载器、碰撞层生成器、注册表三个模块。

**三件事，开工前必须知道。**

1. 克隆后第一件事是启用钩子：git config core.hooksPath .githooks。不启用的话，契约混提交与错误提交信息只会在 CI 上被抓，反馈慢一轮。
2. 大文件不入库：web/public/models/ 下的 .glb 已被 .gitignore 排除。模型走网盘或局域网共享，仓库只留清单与校验和；否则一次 git clone 会拖到天亮。
3. 契约只读：contracts/ 不在任何人的日常改动手册里。它的变更有独立流程（第十五章），且被三层机器拦截。
另外两处与 V2 的差异，是踩过坑换来的：

1. CI 的变异 job 依赖前两个 job，而不是并行。变异验证要反复改文件重跑，并行到同一 workspace 上会互相污染。
2. 变异脚本每次运行前清 `__pycache__` 并加 `-B`。首个 CI 运行就因为这个失败：0.40 -> 0.30 前后文件大小相同，CI 上变异与还原落在同一整秒，.pyc 按「mtime(秒) + 大小」判定有效，还原后仍加载变异字节码，于是「还原后重跑仍有失败」。本机因为每次跑都跨秒而从未暴露。这条已按同秒还原场景复现并修复。

# 十五、GitHub 协作：分支、提交、推送与合并

规范的目标不是"好看"，是**让把关人能在 3 分钟内判断一个 PR 该不该合**。完整版见 `docs/branch-commit-spec.md`，这里是要点。

## （一）分支

**表 36 分支类型与命名**

| 分支 | 谁用 | 命名 | 规则 |
| --- | --- | --- | --- |
| main | 全员只读 | — | 禁止直推；本地 pre-push 拦截，CI 二次校验 |
| 功能分支 | 每人 | `feat/<步骤号>-<短名>`，如 feat/2-1-grab-action | 合并后删除；同时最多一个未合并分支 |
| 修复分支 | 每人 | `fix/<现象短名>`，如 fix/grab-scope-jump | 合并后删除 |
| 契约分支 | 任何人 | `contract/<改什么>`，如 contract/doors-width | 只含 contracts/；标题以 [CONTRACT] 开头 |
| 演示分支 | 设计 A | `demo/<场景>` | 彩排期临时隔离，不得存活过夜 |

**一人同时最多一个未合并分支。**分支活过 4 小时视为风险：要么拆小合并，要么废弃。这一条是为了让审核队列永远是短的——队列一长，把关人就会开始"看着差不多就合"，闸门就失效了。

## （二）提交信息

```
提交信息格式（commit-msg 钩子强校验）
<type>(<scope>): <摘要>

<可选正文：为什么这么改，而不是改了什么>

Authored-by: ai | human | ai+human
Step: 2.1

示例：
feat(robot): 2.1 抓取改为水平距离判定并使用 attach 挂载

抓取不再做手部碰撞检测；距离小于 1 米即判定成功。
挂载统一 attach()，避免 add() 造成的瞬移。

Authored-by: ai+human
Step: 2.1
```

`type` 取 `feat / fix / test / docs / contract / chore / refactor / perf`；`scope` 是模块名（robot、nav、scene、ui、server、rules、layout、ci）；摘要带步骤号，方便对照本方案查进度。`Authored-by` 不是追责，是让审核决定看多细：`ai` 就按"AI 典型坑"逐项过，`ai+human` 重点看人改过的那几行有没有破坏原测试。

## （三）推送与合并

1. 完成后推自己的分支：git push -u origin feat/2-1-grab-action。推 main 会被 pre-push 拒绝。
2. 开 PR：gh pr create --fill --base main。PR 模板会自动带上三关自检与"变红证据"栏位，必须逐条勾选并粘贴证据。
3. 等 CI 四个 job 全绿（契约闸门 / 后端测试 / 变异验证 / 前端测试）。红了不要找人看，先自己按日志修。
4. 把关人 approve 后，用 Squash and merge 合并，PR 标题即最终提交信息；合并后删远端分支。
5. 里程碑 tag 只由把关人打，避免自己给自己发奖。

## （四）三层机器拦截

规则写在文档里会被忘记，写成设施才会生效。契约相关的三层拦截如下，作者绕不过去：

**表 37 契约闸门的三层拦截**

| 层 | 机制 | 拦截什么 |
| --- | --- | --- |
| 提交时 | .githooks/pre-commit 调 check_contracts.py --staged | 契约与代码混提交；改了契约但没刷 lock |
| 推送时 | .githooks/pre-push | 直推 main（可用 HOMETWIN_ALLOW_MAIN_PUSH=1 单次豁免，仅把关人初始化时用） |
| 合并时 | CI contract-gate job | lock 与磁盘不一致；混提交；PR 标题缺 [CONTRACT] 前缀；业务代码反向依赖 scripts/ |

三种典型作弊都已被实测拦下：

**表 38 契约闸门的实测拦截记录**

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| AI 为跑通而删 required，并顺手改业务代码 | 拦下 2 项 | lock 不一致 + 混提交，双报 |
| 只改 Schema 没刷 lock | 拦下 1 项 | 指纹不匹配 |
| 规范的契约 PR（只含 contracts/ + 刷 lock + 写 CHANGELOG） | 通过 | 闸门放行，指纹更新 |

## （五）一个必须现在决定的取舍

**GitHub 私有仓库在免费账户下无法开启分支保护**（API 返回 403：需 Pro 或公开仓库），Rulesets 同样不可用。这意味着"禁止直推 main""必须 review 后才能合并"这两条在服务端不生效，只剩下本地 `pre-push` 钩子——而钩子是本地的，`--no-verify` 或者换台机器就能绕过。

**表 39 三种处置方案**

| 方案 | 成本 | 效果 | 代价 |
| --- | --- | --- | --- |
| 保持私有 + 纯人工 | 0 | 钩子 + CI + 把关人亲自合并，够用 | 依赖人不手滑；CI 红也能合 |
| 升级 GitHub Pro | 约 4 美元/月 | 分支保护、必需检查、必需 review 全部生效 | 要付款；26 小时内最省心的选项 |
| 仓库转公开 | 0 | 分支保护免费可用 | 代码公开，比赛作品需确认是否允许 |

**我的建议：先按"保持私有 + 纯人工"走**，因为四人小团队 + 26 小时窗口，最坏情况是一个人误推 main，恢复成本是 `git revert` 一次，而不是灾难。若队内已有人有 Pro，用它换来的确定性值这个钱。转公开不建议，除非已确认不影响参赛资格。当前仓库已处于"钩子 + CI 全绿"的状态，人工关卡由把关人执行第十六章流程。

## （二）三关流程

### 第 0 关：契约（30 秒，机器判）

```
把关人的三条命令
```

### 第 1 关：测试有效性（90 秒，最容易被糊弄的一关）

**表 41 第 1 关检查项与一票否决**

| 检查 | 一票否决条件 |
| --- | --- |
| 是否含测试文件改动 | 改了逻辑却零测试 |
| 是否贴了"故意改错 → 测试变红"的证据 | 没有，或只说"我本地跑过了" |

| --- | --- | --- |

3. 若对应里程碑，由你打 tag。

## （三）一票否决清单（背下来）

1. 改契约混进业务代码。
2. 没有能失败的测试，或变红证据是假的。
3. 越界改别人模块且未打招呼。
4. 硬编码密钥 / 绝对路径 / 演示台词。
5. 擅自放宽 Schema 让代码通过。
6. 空 catch 掩盖错误且无日志。
7. 状态机存在无法退出的状态。
8. 用了 .add(objectMesh) 形式的挂载（必瞬移）。

## （一）建议 1：3D 视觉表现

**表 46 建议 1 的逐条处置**

| 你的建议 | 处置 | 理由与补充 |
| --- | --- | --- |
| 距离小于 1 米即判定可抓取 | 照做 | 补一条口径：用水平距离，不含高度差。物体在桌面、机器人在地面，算三维距离会永远判不够。示例布局八件物体实测 0.60–0.93 米，已由校验脚本纳入回归。 |
| 固定 45 度正交俯视规避穿帮 | 照做，加两条 | 正交 + 45 度只压住深度方向的穿插；手从侧面伸进柜体仍会露。补：① 抓取时机器人朝向固定为面向目标家具；② 手臂动画幅度不超过物体包围盒。另外锁死 enableRotate=false，否则"固定视角"只是默认值。 |
| Punch 动作快速过渡 | 照做 | 补时限：整段不超过 0.5 秒（含 0.25 秒淡入淡出）。没有上限的"快速"在实现时会变成 1.2 秒。 |
| 物体缩放到 0.4 倍 | 照做，但做成参数 | 0.4 倍在正交视角下会让物体看起来"被吸进了手心"，尤其杯子这类小物件。默认仍取 0.4，但写成配置项，彩排时可对比 0.5 倍。这是唯一一条我认为可能需要现场调数值的建议。 |
| 挂载保持世界变换 | 照做，并变成测试 | 只写规则不够，AI 一定会在某处写 add()。已规定"挂载前后世界坐标差小于 1e-6"作为必测项，并把 .add(objectMesh) 形式写进一票否决。 |
| 不滥用发光特效 | 照做，范围扩大 | 不止"不滥用"，是抓取期间完全禁用发光、描边、粒子：它们会在物体与手之间画出高亮接触线，等于主动标出穿模点。"找到时高亮"保留，但与抓取在时间上错开，不叠加。 |

**要坦白的一点。**这套做法的本质是"让穿帮不被看见"，不是"消除穿帮"。它有效的前提是视角锁死。一旦有人想加"自由旋转看房子"这种展示，防线立刻失效；那时必须回到真正的 IK 或接触约束，成本会翻几倍。这个边界已写进 2.7 节，避免后面有人以为它更万能。

## （二）建议 2：纠错改为强规则

**表 47 建议 2 的逐条处置**

| 你的建议 | 处置 | 理由与补充 |
| --- | --- | --- |
| 不依赖大模型 | 照做，且前置 | 纠错判断从"最后兜底"提到"流水线第 0 档"：纠错句如果先进缓存或进模型，会出现"模型把'不对'当成一句新的找物指令"。现在纠错永不进缓存、永不进模型。 |
| 正则匹配否定词与新地点 | 照做，但分级 | 这是本版改动最大的一处。原方案把所有"改写类"词（应该、挪到、移到、搬到）都当否定词，实测结果是"帮我把书搬到卧室""把钥匙挪到餐桌"这类普通搬运指令会被判成纠错，机器人回一句"抱歉，我记错了"，非常突兀。已改为：硬否定词（不对/错了/放错/别放）一定是纠错；软改写词只在"无祈使包装且不超过 10 字"时才算。附 8 条回归用例。 |
| 强制下发 go(新地点) + drop | 改为两套模板 | 这条在"机器人手里拿着物体"时完全正确；但演示流程里纠正发生在"已经放到茶几上"之后，手里是空的。此时 go + drop 会被语义校验拦住（drop 前必须 grab），现场表现为"说了抱歉但什么都没发生"。所以主路径仍是 go(新地点) + drop，另一条按 holding 分支补成 go(物体) + grab + go(新地点) + drop。两条都是固定模板，都不调模型。 |
| 直接调用记忆纠正接口 | 照做 | 旧位置 −0.30、新位置 0.90，与 V2 一致；新增 source=corrective 与 corrected 字段，让 HUD 与日志能区分"照着做"和"改过来做"。 |
| 五句台词固化本地缓存 | 照做，但改缓存键 | V2 的键是 hash(query + layout_id + 记忆摘要)，而记忆会被观察不断更新，键随之漂移，固化好的缓存就命不中——这是"彩排好好的、现场不灵"的典型来源。改为只按标准化 query（去标点、去唤醒词、小写）。另加一条"每条缓存都必须过语义校验"的测试，防止有人往里塞非法步骤。 |

实测：30 余条用例全部通过，单次判定平均低于 0.1 毫秒；"普通搬运指令不得误判"由 8 条反例守着，且已在变异验证中登记（把软词判定改成恒真，4 条用例立刻变红）。

## （四）建议之外我补的四件事

1. 契约指纹（lock）。只看 diff 能发现"改了契约"，发现不了"改了示例没改 lock"或"手改 lock 掩盖改动"。指纹把这件事变成算术。
2. 变异脚本自身的有效性判据。第一版脚本把多行替换写成字面量反斜杠 n，语法错误让 pytest 以退出码 2 中断，被误判成"测试抓住了"——一个能自洽出绿灯的假证据。现在退出码 2 一律判无效（INVALID），且只用单行锚点。这条经验的价值超出本仓库：任何"证明测试有效"的工具，本身也要能失败。
3. "有错"不等于"抓对错"。布局检查器第一版只断言"报了错"，变异验证发现把"够不着"整段关掉测试仍全绿（因为别的检查也在报错）。已改为断言具体错误类别。这直接对应你担心的"AI 写的测试看起来绿其实无效"。
4. 把关人瓶颈。这是你的方案里没提但最可能拖垮进度的一条：四个人同时产出，一个人审。已加固定审核窗口、限时、PR 拆分要求，以及"授权 AI-D 代审非契约 PR"的降级方案。

# 十九、后续迭代方向

赛后若继续推进（例如作为课程项目、论文原型或产品原型），建议按以下顺序迭代。每一项都在现有架构上增量完成，不推翻已有模块；这也是当初把场景、执行、认知三层分开的回报。

**表 49 迭代路线**

| 优先级 | 方向 | 做法 | 依托资源 |
