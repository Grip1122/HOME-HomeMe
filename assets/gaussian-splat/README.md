# 建筑高斯泼溅素材（项目视觉基点）

> **本项目所有场景表现以这份素材为基点。** 它是真实建筑的高斯泼溅重建。**决定（10/31）：以它为唯一场景来源，不做灰盒。**后续的家具体块、机器人走位、相机参数，都要能落在这份重建出的空间里。

## 1. 为什么它决定了整个技术路线

最初的方案（V3 初稿）走的是"程序生成的灰盒房间 + RobotExpressive 机器人"，现已取消。拿到这份素材后，**场景的视觉起点变了**：真实建筑的点云重建取代了程序化的房间轮廓。这带来三个必须现在就说清的后果：

| 影响 | 说明 |
| --- | --- |
| **寻路网格不能凭空画** | 网格必须落在重建出的地面范围内，"可通行"要由点云的地面高度决定，而不是手写矩形 |
| **家具位置要与点云对齐** | 现有 `layout_A.json` 的家具坐标是程序化假设，需要按点云实测重新标定 |
| **渲染路线要分两档** | 高斯泼溅（视觉）+ 几何体（逻辑与碰撞）叠加，不是二选一 |

**不改变的部分**：五个动作的语义、状态机、`/plan` 契约、纠错强规则、记忆模型、测试与守门设施。它们与场景怎么渲染无关——这正是当初把逻辑层和视觉层分开的回报（见总览第 2.7 节）。

## 3. 空间实测（供坐标标定用）

| 指标 | x | y | z |
| --- | --- | --- | --- |
| 全量最小 | −26.22 | −11.58 | −12.35 |
| 全量最大 | 9.82 | 3.41 | 6.87 |
| 跨度 | 36.05 | 14.99 | 19.23 |
| 1% 分位 | −4.09 | −3.03 | −1.95 |
| 99% 分位 | 3.53 | 0.06 | 1.94 |
| 质心 | 0.11 | −0.73 | −0.08 |

**读法**：全量包围盒（36×15×19 米）远大于 1%–99% 分位区间（约 8×3×4 米）。说明外围有稀疏的离群高斯（天空、远景、重建噪声），**真正的主体建筑集中在质心附近**。

**单位未定**。这些数字是重建坐标系下的原始值，不一定是米。标定时必须做一件事：**在场景里量一个已知尺寸**（一扇门约 0.9 米、一张桌高约 0.75 米），据此求出缩放系数，再写进 `core/config.js` 的 `sceneScale`。在没量之前，任何"这是几米"的判断都是猜的。

**y 轴方向也未验证**：常规 3DGS 输出的 y 轴向上，但需实测确认；若是 z 轴向上，前端加载时要转一次。

## 4. 存放位置（为何仓库里没有这个文件）

单文件 449 MiB，**超过 GitHub 普通提交 100 MB 的单文件上限**，直接推会被服务端拒绝。因此：

- 仓库内保存：本说明 + `manifest.json`（校验和、来源、尺寸）
- 原始 `.ply` 存放：**网盘**（链接写进 `manifest.json`），以及 sen（设计 B）与 Jesu 的本地各一份；另在 GitHub Release `splat-v1` 存一份（上传完成并核对 sha256 后才算数）
- `.gitignore` 已排除 `assets/gaussian-splat/*.ply`，防止有人误提交

若确需版本化，可选 Git LFS（免费额度 1 GB 存储 / 1 GB 月流量，单文件 449 MB 会占掉近一半），**不推荐**：这是静态素材，不需要版本历史。

## 5. 使用前必须先做的三件验证

在任何人开始写渲染代码之前，先确认这三条。任何一条不成立，方案要改：

1. **能不能在浏览器里跑起来。** 3DGS 无法用 three.js 直接渲染 `.ply`。需要转换并接入高斯泼溅渲染器：`antimatter15/splat`（最轻）、`mkkellogg/GaussianSplats3D`（three.js 集成）、或 `playcanvas` 引擎。先用现成 viewer 打开原文件确认观感，再决定接入哪个。
2. **点云与几何体能否共用一套相机。** 逻辑层要的是正交固定视角（总览 2.7 节），高斯泼溅在正交相机下的表现需实测——它按屏幕空间投影排序，正交投影可能出排序错误。**这条不成立，"固定视角规避穿模"的方案要重新设计。**
3. **帧率。** 200 万高斯在普通笔记本上能否到 30 帧。若不能，需要抽稀（降到 50–80 万）或分块加载。

### 5.1 实测结果（10/31，Jesu）

环境：Windows 11，Chrome（有头，ANGLE/D3D11），RTX 5060 Laptop；渲染器 `@mkkellogg/gaussian-splats-3d` 0.4.7 + three 0.187，球谐取 0 阶。实验脚本在仓库外，结论如下。

| 验证 | 结论 | 依据 |
| --- | --- | --- |
| 1. 浏览器能否跑 | **成立**。GaussianSplats3D 直接读原始 `.ply`，**不需要转 `.ksplat`** | 449 MB 加载约 5 秒，读入 1,978,997 点 |
| 2. 正交相机能否用 | **成立**。切掉屋顶后，45° 正交俯视在东南西北四个方向和正俯视下都没有排序错乱或鬼影 | 截图见下表；与同位姿透视图逐张对照 |
| 3. 帧率 | **成立，不用抽稀**。透视 213 fps，正交 198–240 fps | rAF 计数 2–3 秒取平均 |

| 截图 | 内容 |
| --- | --- |
| `shots/p45_south_ortho.jpg` | 正交 45° 俯视（目标视角） |
| `shots/p45_south_persp.jpg` | 同位姿透视，对照用 |
| `shots/top_down_ortho.jpg` | 正交正俯视，可直接读出平面布局 |

**必须知道的三个坑：**

1. **屋顶必须切掉。** 不切的话，45° 俯视整个画面被屋顶和离群点糊住，什么都看不出来。实测按原始坐标 `y > -1.6` 裁剪（下面第 2 条说明为什么是负数），再用 1%–99% 分位框外扩 0.3 去掉外围离群点，剩 181 万点。
2. **原始坐标 y 轴向下。** 相机 `up = [0,-1,0]` 时画面才正立；高度直方图里地面峰在 y≈0，屋顶在 y≈-3.0。与 `web/src/scene/scene-transform.js` 的 `rawToSim` 用 `-y` 一致。
3. **演示机必须走独显。** Chrome 默认走 AMD 610M 核显，只有 **8 fps**；加启动参数 `--force_high_performance_gpu`，或在 Windows「图形设置」里把 Chrome 设为高性能，才走 RTX 5060。路演前要在现场机器上确认。

**还没做的**：靠近墙边和镜头前景（画面下沿）有大片拖影，这是重建素材本身在相机没拍到的区域的质量问题，不是排序错误。固定视角时把这些区域留在画框外即可。
