# AI 辅助开发规则

> 对应方案 0.3。三个问题：AI 写的代码在异步、状态机、边界上容易崩；AI 会为了跑通而擅自改接口 Schema；AI 写的测试经常是假绿。
> 这份规则不靠自觉，靠**机器拦截 + 人工第一关**。

---

## 规则一：必须附带单元测试

| 要求 | 怎么执行 |
|---|---|
| 每个模块至少 3 条测试：正常 / 边界 / 异常 | PR 模板第 1 关勾选；审核清单第 1 关核对 |
| 异步代码必须测「中途取消」与「并发调用两次」 | 审核清单第 2.2 节“异步竞态”“假单飞锁” |
| 状态机必须测「非法转移」 | 同上“状态机死锁” |
| 测试名写成句子（`test_study_does_not_become_book`） | 失败信息自带语义，审核时一眼看出覆盖点 |
| 不得为了让测试过而改测试预期、删断言 | 任务卡约束 5；审核时看测试文件 diff 有无“删断言” |

---

## 规则二：测试必须被“故意改错”验证过

**绿灯不是证据，变红才是。**

作者提交 PR 前，必须对自己的核心逻辑做一次破坏，确认测试变红，并把输出贴进 PR。

### 方式 A：手工改错（最小成本）

```bash
# 1. 找到核心判断，例如 grab 的距离阈值
#    把 `dist < 1.0` 改成 `dist < 100.0`
# 2. 跑测试
npm test -- actions        # 或 python -m pytest tests/test_xxx.py
# 3. 必须出现失败，把终端输出贴到 PR 模板“变红证据”
# 4. 改回去，确认回到全绿
```

### 方式 B：自动变异（仓库已内置，后端强制）

```bash
python scripts/mutation_demo.py            # 全部变异
python scripts/mutation_demo.py -k rules   # 只跑规则相关
```

脚本对 11 处关键逻辑逐一施加破坏，验证期望的测试变红，然后自动还原。CI 的 `mutation` job 每个 PR 都会跑。

**新增核心逻辑时，同步在 `scripts/mutation_demo.py` 的 `MUTATIONS` 里登记一条变异。**

### 变异脚本本身也会写错

本仓库第一版变异脚本就出过问题：多行替换写成了字面量 `\n`，造成语法错误，pytest 以退出码 2 中断，被误判成“测试抓住了”。修复后的判定规则：

| 结果 | 含义 |
|---|---|
| `KILLED` | 期望的测试失败了 |
| `KILLED_OTHER` | 有测试失败，但不是预期的那条（覆盖点漂移，要复核） |
| `MISS` | 改坏代码测试仍全绿 → 测试无效 |
| `INVALID` | pytest 退出码 2（语法/收集错误）→ 不算数 |

另一次发现：布局检查器原先只断言“有错误”，漏了对“够不着”这类的具体断言，变异验证把它抓了出来——这是“测试看起来在测、其实没覆盖”的典型。

## 规则三：Code Review 第一关——契约 diff

**审核第一步永远是这一条，在读任何业务代码之前：**

```bash
git diff origin/main --stat -- contracts/
```

| 结果 | 动作 |
|---|---|
| 输出为空 | 通过，进入第 1 关 |
| 有输出，且 PR 标题以 `[CONTRACT]` 开头、只含 contracts/ | 按契约 PR 流程审（见 `contracts/README.md`） |
| 有输出，但 PR 同时改了业务代码 | **直接打回**，要求拆成两个 PR |
| 有输出，但标题不是 `[CONTRACT]` | **直接打回** |

### 三层机器拦截（作者无法绕过）

| 层 | 机制 | 位置 |
|---|---|---|
| 提交时 | `pre-commit` 钩子调 `check_contracts.py --staged` | `.githooks/pre-commit` |
| 推送时 | `pre-push` 禁止直推 `main` | `.githooks/pre-push` |
| 合并时 | CI `contract-gate`：lock 一致、不混提交、标题前缀 | `.github/workflows/ci.yml` |

### 指纹文件

`contracts/contracts.lock.json` 记录每份契约文件的 SHA-256。任何人改了契约却没刷指纹，闸门直接失败。**不要手改 lock**，只能 `python scripts/check_contracts.py --update-lock`，且该提交只能含 `contracts/`。

### 为什么这样设计

AI 最常见的偷懒方式是“让代码跑通的最短路径”——放宽 `required`、加宽枚举、新增一个随便什么字段。这种改动**在业务代码里看不出来**，只有 `contracts/` 的 diff 会暴露。所以：

1. 不让契约和代码同批提交（混提交会淹没契约 diff）；
2. 不让契约改动绕过 lock；
3. 任务卡里明确写「不得修改 contracts/，认为契约有问题就停下来写说明」。

## 规则四：AI 生成与人工修改要可追溯

每个提交的 `Authored-by:` 行（`ai` / `human` / `ai+human`）由 `commit-msg` 钩子强制。用途不是追责，而是审核时：

- `ai`：整段按审核清单第 2.2 节“AI 典型坑”逐项过；
- `ai+human`：重点看人改过的那几行是否破坏了原测试；
- `human`：按普通代码审。

---

## 规则五：AI 不确定时的出口

AI 常见的另一种失败是“硬编一个看似合理的实现”。任务卡里要求 AI：

> 若你发现契约有歧义、验收用例互相冲突、或缺少做出决定所需的信息，**停下来写问题清单，不要自己猜**。

人工审查时，AI 输出的「我做了哪些假设」那一段，是审核优先级最高的内容。
